# DB500 UDP CONTROL 通信扰动与稳定性测试方案

状态：`PLANNED_SCIENTIFICALLY_REVIEWED`

## 1. 测试目的

本测试验证 CONTROL V1 在 UDP 数据报丢失、重复、乱序、延迟、突发和格式异常条件下，是否仍然
满足以下性质：

- 合法请求严格按照 `request_id` 顺序访问寄存器；
- 同一通信代际内，每个 `request_id` 最多访问一次寄存器；
- RESPONSE 丢失后重发同号请求，只重放首次结果，不重复执行；
- 有界窗口和 UDP 缓存耗尽时允许丢包，但不得形成跨层永久死锁；
- 可恢复异常由主机重试完成；重试耗尽后，能够通过 CONTROL 静默 watchdog 建立新通信代际；
- 恢复后链路保持 Up，CONTROL 从 `request_id=1` 重新工作，配置寄存器值不被通信复位清除；
- 所有未注入的回复字段、端点、长度和内容均符合 CONTROL V1。

测试允许出现符合注入模型的丢包、超时和重传。任何重复寄存器访问、越序访问、错误回复、窗口
状态跨代残留、无法按规定流程恢复或 TEMAC 链路被 CONTROL 故障拖死，均判定为失败。

## 2. 被测范围与分层

### 2.1 当前固件黑盒测试约束

本轮稳定性测试只使用板上当前已下载的 `udp_control_test_top` 固件。允许修改主机测试脚本、生成
主机日志和抓包，但不修改 FPGA RTL、testbench、Vivado fileset 或约束，不重新综合、实现、生成
或下载 bitstream，也不新增或启用 ILA/VIO。磁盘基准镜像 SHA-256 为
`021B0DC22234F45FE71F9131F5B87C122A9BBC6CAB26B409ECFEE7AAC559076A`；板上身份沿用该镜像最近一次
下载记录、CONTROL签名和既有板测连续性确认，不声称能够从运行器件反读并计算相同哈希。

本轮能够使用的定位证据止于主机事件日志、Windows捕获点、现有线上回复、测试寄存器和链路
状态。遇到需要新增ILA或修改可观测寄存器才能继续区分的问题时：

- 保留失败seed、事件轨迹、抓包、前后健康检查和当前能证明的最小故障边界；
- 结果标记为 `FAIL_UNLOCALIZED` 或 `INCONCLUSIVE_LOCALIZATION`，不继续修改固件定位；
- “没有定位到具体RTL状态”不把实际语义失败降级为通过；
- D16、D17a、D17b等需要主动控制内部ready的项目不在本轮板级黑盒覆盖率中冒充已执行，引用
  既有仿真结论时必须明确标成历史证据。

本节约束只限制本轮测试动作，不改变第9节描述的完整证据等级，也不否认未来在另一次获批活动
中使用ILA或专用诊断镜像的价值。

当前板级被测路径为：

```text
host CONTROL model
        │
        ├── request fault injector
        │
Windows UDP socket / ASIX NIC
        │
direct Gigabit Ethernet link
        │
PCS/PMA + TEMAC + Ethernet client FIFO
        │
IPv4/UDP parser + RX/TX payload ring
        │
db500_udp_control
        │
db500_ctrl_test_reg_bank
        │
        └── response fault injector ──> host CONTROL model
```

首轮在现有 `udp_control_test_top` 镜像上完成，不修改 RTL。主机测试程序在逻辑请求进入 socket
之前以及 socket 收到 RESPONSE 之后注入故障。这能够等价验证请求未到达、重复到达、不同顺序
到达以及主机未收到回复等 CONTROL 语义。

这种主机内故障注入验证的是端到端协议在相同可见结果下的行为，不声称数据报真的在线缆、网卡
或交换设备中被丢弃和延迟。凡是需要定位实际物理丢失点、真实线上顺序或线路误码的结论，必须
使用相应层级的额外观测手段，不能由主机模型模拟结果替代。

以下故障不与 CONTROL 数据报扰动混为一类：

- FCS 错误、模拟电气噪声和收发器误码属于物理链路测试；普通 UDP socket 无法生成错误 FCS；
- 拔线、PHY 重协商、PCS/PMA 失锁属于链路恢复测试；
- FPGA 时钟停止、配置丢失或逻辑完全不运行属于人工或系统级恢复范围；
- DATA 满载共存等待双端口 DATA 架构实现后另行增加。

## 3. 测试基线

### 3.1 硬件与网络

| 项目 | 基线值 |
|---|---|
| FPGA 镜像 top | `udp_control_test_top` |
| FPGA | Kintex-7 `xc7k325tffg676-2` |
| 主机接口 | ASIX USB 千兆网卡“以太网 2” |
| 主机端点 | `192.168.1.10:32000` |
| FPGA 端点 | `192.168.1.20:32000` |
| 链路 | 1 Gbit/s，全双工，直连 |
| CONTROL payload | 固定 16 Byte |
| 窗口 | W=4 |
| watchdog | 500 ms 完全静默 + 100 ms 主机保护时间 |

开始扰动测试前必须先执行一次无扰动基线：连续完成 QUERY/SET、W=4、乱序窗口、丢回复重放、
60 秒压力和普通静默跨代恢复。基线失败时不得继续用随机扰动掩盖基础问题。

每轮测试记录 bitstream SHA-256、网卡型号和驱动版本、端点、链路速率、网卡 offload/节能设置、
脚本版本、配置文件摘要、随机种子和开始/结束时间。若镜像身份不等于当轮指定身份，本轮结果
无效。正式对比轮次必须使用相同的网卡设置；设置变化要作为新的环境分组报告。

### 3.2 测试寄存器判据

现有测试 bank 提供：

| 地址 | 属性 | 用途 |
|---:|---|---|
| `0x0000` | RW | `scratch0`，验证 SET 和 QUERY |
| `0x0001` | RW | `scratch1`，验证 SET 和 QUERY |
| `0x0010` | RO | 固定签名 `0xDB500001` |
| `0x0011` | RO | 成功 scratch 写入计数；验证 SET 最多执行一次 |
| `0x0012` | RO | watchdog 软复位次数 |
| `0x0013` | RO | watchdog 最近复位原因 |

`write_count` 是 SET 去重的主要硬件判据。每个计划成功的 scratch SET 只允许使其增加 1；请求或
回复被重复任意次数，都不得额外增加。最终还要 QUERY 两个 scratch，和主机参考模型逐项比较。
但“最终值 + write_count”不能单独证明中间执行顺序：一次漏写和另一次重复写可能抵消计数，多个
SET 越序也可能得到相同最终值。

因此确定性乱序用例和随机请求流必须包含可观测的数据依赖链。基准四请求为：

```text
N+0  SET   scratch0 = A
N+1  QUERY scratch0      必须返回 A
N+2  SET   scratch0 = B
N+3  QUERY scratch0      必须返回 B
```

四条请求可按任意线路顺序到达，但两个 QUERY 结果只能按照编号顺序计算。随机长稳测试持续生成
唯一 SET 数据并穿插 QUERY 检查点，由参考模型按 `request_id` 顺序计算期望值。若仍出现无法从
寄存器结果和抓包区分的顺序争议，再启用 FPGA 执行边界 ILA；不能用最终值推测执行顺序。

除专门改变超时的边界试验外，主机重试采用 CONTROL V1 基线：初次等待 2 ms，第一次同号重发
等待 4 ms，第二次同号重发等待 8 ms；总计三次发送仍无合法回复时停止全部 CONTROL 流量，转入
静默恢复。随机测试不得用无限重试掩盖恢复失败。

## 4. 故障注入模型

### 4.1 可复现事件

每个随机决定都必须由显式 64-bit `seed` 产生，并写入 JSON Lines 事件日志。最少记录：

```text
event_index, monotonic_time, seed, generation, direction, request_id,
logical_attempt, action, scheduled_time, actual_time, payload_hash, result
```

不能按异步回复实际到达顺序连续消费同一个全局随机数流，否则操作系统调度差异会改变后续故障
序列。实现必须采用以下任一方式：

- 测试开始前生成本轮完整逻辑故障计划；或
- 用 `{seed, generation, direction, request_id, logical_attempt, fault_type}` 独立确定每个决定。

同一脚本版本、配置和 seed 必须能够重建相同的逻辑故障计划；JSONL 事件轨迹还必须能够绕过
随机生成器直接重放。seed 重建的是计划，不承诺 Windows 调度、socket 到达时间或网卡发送时刻
逐纳秒相同。实际时间差异单独记录并按第 9 节的证据等级解释。

### 4.2 数据报级动作

| 动作 | 请求方向实现 | 回复方向实现 | 验证内容 |
|---|---|---|---|
| `PASS` | 正常发送 | 正常交给主机模型 | 基线 |
| `DROP` | 本次不调用 `sendto` | socket 收到后不交给模型 | 请求丢失、回复丢失 |
| `DUPLICATE` | 同一 payload 发送 2～3 次 | 同一回复向模型交付 2～3 次 | 去重和主机幂等处理 |
| `DELAY` | 延后调用 `sendto` | 收到后延后交付 | 超时、同号重发和迟到回复 |
| `REORDER` | 多条请求进入调度队列后换序发送 | 多条回复缓存后换序交付 | W=4、有序执行和主机按编号归并 |
| `BURST_DROP` | 连续丢弃 2～4 次发送 | 连续丢弃 2～4 条回复 | 短时网络中断 |
| `BLACKOUT` | 指定时间内不发送 | 指定时间内不交付 | 重试耗尽和 watchdog 恢复 |
| `MALFORMED` | 发送定向构造的非法 payload | 不适用 | decoder 丢弃和后续恢复 |

回复侧 `DROP/DELAY/REORDER` 模拟的是上位机可见结果，不改变 FPGA 已经发送回复这一事实；这正是
验证结果保留和同号重放所需的语义。需要证明数据报确实在物理线路中被设备丢弃时，必须另加
透明网络损伤设备，不能把主机“收到后忽略”描述为线路证据。

普通随机轮次中，单个数据报的 `DROP`、`DUPLICATE` 和 `REORDER` 选择互斥；未被DROP的报文再按
该等级的独立DELAY概率决定是否延迟。`BURST_DROP` 和 `BLACKOUT` 是独立的高优先级状态，激活时
覆盖单包选择。确定性组合测试若需要复制后分别延迟，必须在用例中显式写出副本数、每个副本的
延迟和最终是否丢弃，不能依赖未定义的动作叠加顺序。

故障注入器投入随机测试前先执行两项自检：全 PASS 模式必须与原无扰动基线一致；强制逐个产生
DROP、DUPLICATE、DELAY、REORDER、BURST_DROP 和 BLACKOUT 时，事件日志与主机模型观察数量
必须一致。注入器自检失败时，随机测试结果无效。

### 4.3 格式异常集合

格式异常使用独立确定性用例，不混入正常请求编号流，并按实际丢弃层分类：

- UDP 层：0-Byte payload、超过 1472-Byte payload、错误 UDP 长度或 checksum；
- CONTROL decoder：1、15、17 Byte payload；
- 未定义消息码；
- REQUEST `status != 0`；
- `request_id=0`；
- QUERY 的 `data != 0`；
- 同一 `request_id` 使用不同类型、地址或数据；
- 只读地址执行 SET、非法地址执行 QUERY/SET。

UDP层异常不得提交 CONTROL payload；CONTROL长度/字段异常必须被 decoder 丢弃。二者都不能
访问寄存器，但必须根据对应层的计数或仿真事件归因。同号不同内容、权限或地址错误按照
CONTROL V1 进入相应的冲突或寄存器 ERROR/fail-stop 路径，并执行规定的静默恢复。

应用层非法 payload 可以通过普通 UDP socket 注入。UDP checksum 错误需要 raw packet/Npcap 或
外部损伤设备；FCS 错误需要 MAC/物理层测试条件，二者不作为首轮脚本的伪造结果。

## 5. 确定性测试矩阵

每项测试使用独立通信代际，或从已知的 `A=E=1` 状态开始。测试结束后执行健康检查：读取签名、
scratch、写计数和 watchdog 计数，并完成一组无扰动 W=4 请求。

| ID | 场景 | 注入序列 | 必须满足的结果 |
|---|---|---|---|
| D01 | 无扰动基线 | 顺序发送 1～4 | 全部完成，字段正确，无重试 |
| D02 | 首请求丢失 | 依赖链中丢弃 1，发送 2、3、4，随后重发 1 | 补回 1 前无2～4回复；两个QUERY最终返回顺序模型期望值 |
| D03 | 窗口内乱序 | 依赖链按4、2、3、1发送 | 两个QUERY分别返回A、B，证明实际访问顺序为1、2、3、4 |
| D04 | 请求重复 | 请求在执行前、执行中和完成后各重复 | 每个编号最多访问一次；完成后重复取得原回复 |
| D05 | SET 回复丢失 | 执行 SET，丢弃首次回复，再发同号 SET | 写计数只增加 1，回复内容与首次结果一致 |
| D06 | QUERY 回复丢失 | QUERY 1读到A并丢回复；SET 2写B；再发原QUERY 1 | QUERY 1重放A而不是B，不重新读寄存器 |
| D07 | 回复乱序/重复 | 对已收到回复换序并复制后交给主机模型 | 主机按编号归并，不错误推进累计确认 |
| D08 | 超窗口请求 | 等待 1 时先发送 5，再完成 1～4并重发 5 | 首个 5 不执行；进入额度后重发才执行 |
| D09 | 同号不同内容 | 同一编号发送不同地址或数据 | 原槽不被覆盖，进入 `fault_hold`，后续不执行 |
| D10 | 格式异常 | 依次发送第 4.3 节非冲突非法记录 | 全部不访问寄存器；随后合法请求正常工作 |
| D11 | 地址/权限错误 | SET只读地址或访问非法地址 | 返回 ERROR，随后进入 fail-stop，不执行后续请求 |
| D12 | 短突发丢失 | 连续丢弃 2～4 次请求或回复 | 同号重试后恢复，无重复执行 |
| D13 | 短网络黑洞 | 双向阻断 20～100 ms | 重试可能耗尽；按静默流程建立新代际 |
| D14 | 持续异常流量 | fail-stop 后仍持续发送重复/非法 CONTROL | watchdog 不触发；停止全部发送后才触发一次 |
| D15 | 普通空闲跨代 | 正常完成后静默至少 600 ms | watchdog 一次复位；从 1 重启；scratch 保持 |
| D16 | UDP接收资源隔离 | 仿真中阻塞 CONTROL 消费并填满 RX ring | 后续帧以FIFO-full丢弃；UDP parser不向Ethernet RX AXIS传播永久反压 |
| D17a | CONTROL→UDP反压 | 分别随机拉低 descriptor ready和payload data ready | encoder字段/字节保持稳定，解除后恰好提交一条完整回复 |
| D17b | UDP→TEMAC反压 | 随机拉低Ethernet TX AXIS ready | TX engine和UDP ring保持当前帧，解除后继续且只释放一次槽 |
| D18 | 恢复后回归 | 每次异常恢复后执行连续 W=4 | 链路仍 Up，CONTROL 完整恢复，无旧请求/回复泄漏 |

D16、D17a、D17b 需要 XSim 控制内部 ready，属于仿真故障注入；当前快速测试寄存器和千兆线路
不能稳定地在板上制造相同内部条件。D16只直接证明Ethernet RX AXIS边界不会被UDP层永久反压，
不能单凭transport级仿真推导TEMAC内部FIFO状态。TEMAC级健康由板级过载后的无扰动恢复检查验证；
出现争议时增加TEMAC RX/TX AXIS ILA。板级随机测试不得用“没有自然遇到FIFO满”代替这些结论。

## 6. watchdog 跨代边界

### 6.1 验收范围

当前协议没有 session/epoch 字段。watchdog 恢复成立依赖以下条件：

- 主机在重试耗尽后停止全部 CONTROL 新请求和重发；
- 从最后一次 CONTROL 发送起保持至少 500 ms 完全静默，再等待 100 ms 保护时间；
- 直连网络不会把旧 CONTROL UDP 数据报保存超过该静默期后重新释放；
- 主机关闭旧 socket、丢弃旧回复并从 `request_id=1` 重建完整必要配置。

普通随机扰动的单包延迟上限必须小于 500 ms；长于该值的事件转入边界特性测试，不得与常规
验收统计混合。

### 6.2 跨代旧包特性测试

专门把旧请求扣留超过 600 ms，并在新代际开始后释放，用于确认当前协议边界：

- 若旧编号远离新窗口，应被窗口规则丢弃；
- 若旧编号恰好落入新代际当前窗口，V1 没有线上信息判断它属于旧代际，不能承诺拒绝；
- 该现象不是随机测试工具应隐藏的失败，也不能记录为 watchdog 已解决；
- 如果产品网络可能长期排队或重放旧 UDP 数据报，必须重新评审 session/epoch，而不能只扩大
  watchdog 时间。

本项是适用边界测量，不纳入当前直连网络的 V1 通过率，但结果必须单独记录。

主机注入器在新代际后才调用 `sendto`，只能证明“跨代旧内容重放”的协议结果，不能证明数据报
曾在真实网络中滞留。要验证“主机在旧代际已经发送、网络静默期间由中间设备持有、复位后才
释放”，必须使用透明Linux bridge/netem、网络损伤仪或等价中间设备。两种测试使用不同名称和
结果分类，不得互相替代。

## 7. 随机扰动阶段

完成全部确定性用例后，按以下推荐强度逐级运行。每一级至少使用 3 个固定 seed，以最少完成
请求数和最少实际注入数作为结束门槛；任一门槛未达到就继续运行。运行时间只作为吞吐和样本
取得成本的报告数据，不设硬性下限，也不为凑满指定时间继续测试。出现语义失败时停止升级，
先重放保存的事件轨迹，再用相同seed重建计划。

| 等级 | 最少完成请求/seed | DROP | DUPLICATE | REORDER | DELAY概率/范围 | 每种离散随机动作最少注入/seed |
|---|---:|---:|---:|---:|---:|---:|
| R0 冒烟 | 1,000,000 | 0.01% | 0.02% | 0.02% | 0.02% / 0～1 ms | 100 |
| R1 常规波动 | 5,000,000 | 0.1% | 0.2% | 0.2% | 0.5% / 0～2 ms | 1,000 |
| R2 强扰动 | 2,000,000 | 1% | 1% | 1% | 2% / 0～10 ms | 10,000 |

R1每万次请求尝试至少安排一次2包突发丢失；R2每千次至少安排一次2～4包突发丢失。实际注入
计数以事件日志为准，不以设定概率乘请求数代替。

R2 的 200 万请求在 1% 单向随机动作概率下，每类、每方向的期望注入量约为 20,000 次，给
10,000 次硬门槛保留约 2 倍余量。结束条件仍同时检查实际完成请求数和实际注入计数，因此随机
波动、watchdog 恢复或有效流量下降不会造成样本不足时提前通过。此前完成的更长运行可作为附加
长稳证据，不要求后续 seed 重复取得同等请求量。

DROP 概率分别作用于每次请求发送尝试和每条实际收到的回复。REORDER 只在当前 W=4 逻辑窗口
以及回复交付队列内操作，不生成违反主机额度规则的无限未完成请求。BLACKOUT 作为独立事件，
不叠加到普通概率后产生无法解释的复合分布。

R0～R2 以持续可恢复扰动为主；若一个故障使重试耗尽，测试器必须执行完整的静默恢复，不得为了
维持吞吐而继续发送。R3专门统计watchdog恢复的一致性，不追求请求吞吐：开发冒烟可先运行100
次，正式验收至少运行1,000次重试耗尽→静默→编号1恢复循环。若把每轮近似看作独立Bernoulli
试验，零失败时95%单侧失败率上界可用 `3/N` 粗略描述；100次约3%，1,000次约0.3%，若目标低于
0.1%则至少需要约3,000次。该估计只用于报告样本强度，不代替对相关故障和具体失败机制的分析。

## 8. 主机参考模型和判定

主机维护以下独立状态，不能仅以“收到了某个回复”判断成功：

- 当前通信代际和下一个可分配 `request_id`；
- 每个逻辑请求的完整原始字段、发送次数和发送时间；
- 已收到但尚未形成累计连续前缀的回复集合；
- 预计 scratch 值、预计成功写次数；
- 预计 watchdog 恢复次数；
- 每个编号的首次合法 RESPONSE；后续同号 RESPONSE 必须逐字段相同。
- 按 `request_id` 计算的寄存器参考状态和每个依赖 QUERY 的期望返回值。

每轮必须检查：

1. RESPONSE 来源端点、长度、消息码、状态、编号、地址和数据；
2. 每个编号不存在两个不同的合法 RESPONSE；
3. 累计完成前缀只在缺口补齐时推进；
4. SET 重试前后 `write_count` 增量严格等于逻辑成功 SET 数，但不把该计数单独作为顺序证明；
5. 每个依赖QUERY的回复及scratch最终值均等于严格编号顺序下的参考结果；
6. watchdog 恢复前后计数增量符合计划，恢复后第一条请求编号为 1；
7. 异常结束后健康检查全部通过，网卡仍报告 1 Gbit/s Link Up。

出现超时但随后按同号重试完成属于预期恢复事件；以下任一情况立即失败：

- 重复或越序寄存器访问；
- 错误请求改变寄存器；
- 同号回复内容变化；
- 未注入的回复丢失且重试/恢复仍不能完成；
- watchdog 重复复位、无法触发或恢复后沿用旧状态；
- CONTROL 故障造成链路永久不可用；
- 脚本模型、事件日志和线路抓包无法对应同一请求。

## 9. 指标与证据

每轮输出机器可读 JSON 摘要和人可读文本摘要，至少包含：

- seed、持续时间、通信代际数；
- 逻辑请求数、实际发送数据报数、接收回复数；
- 各类注入事件数量；
- 超时、同号重发、重复回复和迟到回复数量；
- 完成请求数、成功 SET 数、硬件 `write_count` 增量；
- 计划时刻到实际 `sendto` 的调度延迟；
- 实际 `sendto` 到 socket 收包的原始 socket RTT；
- socket 收包到交付主机模型的人为注入延迟；
- 逻辑请求首次调度到完成的总延迟；
- 最后一次旧代际发送到新代际首条成功回复的恢复延迟；
- watchdog 预期/实际次数和每次恢复时间；
- 最终 scratch、签名、链路状态和总判定；
- 首个失败事件前后至少 100 条事件记录。

确定性短测试保存全部逐包事件。百万级长稳测试保存全部非PASS注入、重试、恢复、异常和周期聚合
快照，同时在内存中保留最近至少1,000条原始事件；失败时立即固化该上下文。每个随机决定仍可由
`{seed, generation, direction, request_id, logical_attempt, fault_type}` 重建，摘要记录失败所在的
generation、request_id和事件索引。不得为了“全量文本日志”制造无界磁盘写入并反过来扰动被测
时序。

板级R1～R3使用主机侧有界循环捕获，默认上限256 MB、截取前128 Byte；测试失败时立即停止并
保留当时窗口，成功轮次保留捕获计数和按计划抽取的样本。需要全量pcapng的短确定性测试单独执行，
不对千万级长稳进行无界抓包。证据等级固定为：

1. 主机事件日志证明应用计划和socket调用；
2. Windows pcapng证明主机协议栈捕获点看到的报文，不等价于物理线序；
3. FPGA Ethernet RX/TX AXIS ILA证明FPGA边界实际接收或提交顺序；
4. 独立网络TAP、镜像端口或损伤设备证明相应外部链路观测点。

已知Windows/NDIS/ASIX路径曾出现主机应用顺序与FPGA实际接收顺序不一致。正常通过轮次保留前
两级证据即可；发生丢包、乱序或卡死归因争议时，必须升级到能区分争议边界的证据级别，不能把
主机pcapng直接称为线序。FPGA只对真正到达其接收边界的顺序负责。

证据建议保存在：

```text
fpga/led/logs/control_fault_<timestamp>_<seed>.log
fpga/led/logs/control_fault_<timestamp>_<seed>.json
AI-work/reports/control-fault/<timestamp>-<seed>/capture.pcapng
AI-work/reports/control-fault/<timestamp>-<seed>/summary.md
```

## 10. 执行顺序

1. 核对并记录 bitstream 身份、端点、网卡和链路速率。
2. 执行现有无扰动 CONTROL 板级脚本，建立本轮基线。
3. 先完成故障注入器全PASS和逐动作强制自检。
4. 执行 D01～D15 和 D18；乱序项使用依赖链，并保存日志。
5. 在 XSim 中完成 D16、D17a、D17b ready/valid 故障注入回归。
6. 使用固定seed依次执行R0、R1、R2；同时满足请求数和注入数门槛，时间仅作记录。
7. 开发阶段执行R3的100次冒烟，正式验收执行至少1,000次watchdog恢复循环。
8. 分别执行主机跨代重放和具备中间设备时的真实网络滞留测试，不与V1常规验收结果合并。
9. 汇总语义正确性、故障覆盖、恢复统计、分层延迟、吞吐和全部失败证据。
10. 完成最终无扰动W=4与静默恢复回归，确认测试没有留下异常状态。

## 11. 计划实现物

后续执行本方案时新增独立主机入口
`fpga/led/scripts/test_udp_control_fault_injection.py`，不把随机行为加入现有确定性验收脚本。新入口
复用 CONTROL V1 编解码定义，并包含：

- 可复现事件调度器；
- 与异步到达顺序无关的分键随机决定和预生成计划；
- 请求和回复两个方向的故障注入器；
- W=4 主机协议状态机和同号重试；
- 独立寄存器参考模型和依赖QUERY顺序oracle；
- 静默 watchdog 恢复控制；
- JSONL 事件日志、JSON 摘要、事件轨迹重放和seed计划重建两种模式。

确定性用例先实现并逐项通过，再启用概率扰动。测试程序不能修改 FPGA 寄存器语义、放宽协议
判据或通过无限重试掩盖无法恢复的问题。
